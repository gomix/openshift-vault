# S3 Benchmarking with Warp

This note documents a simple and repeatable approach for benchmarking S3-compatible object storage from OpenShift using **Warp**.

The benchmark workloads run as containerized OpenShift Jobs, allowing the tests to be executed directly from the cluster against any
S3-compatible endpoint.

The approach is independent of the underlying S3 implementation and can be used with NooBaa, Ceph RGW, AWS S3, or other S3-compatible services.

## Overview

The basic test architecture is:

    OpenShift
        |
        +-- Job
             |
             +-- Warp container
                    |
                    | S3 API
                    v
              S3 endpoint

Using an OpenShift Job makes the benchmark reproducible and allows the test workload to run from the same infrastructure where applications
consume object storage.

## Prerequisites

- Access to an OpenShift cluster.
- An accessible S3-compatible endpoint.
- S3 access and secret keys.
- A bucket for the benchmark workload.
- Warp container image available to the cluster.

When testing NooBaa, an **ObjectBucketClaim (OBC)** can be used to provision the bucket and credentials.

## Benchmark Workflow

The general workflow is:

1. Prepare the namespace.
2. Provision or identify the S3 bucket.
3. Obtain the S3 endpoint and credentials.
4. Deploy the Warp benchmark workload.
5. Run the desired benchmark.
6. Collect the Warp results.
7. Analyze the results.

## Warp

Warp is an S3 benchmarking tool that can generate different object storage workloads and report throughput, operations per second, and
latency statistics.

The exact workload should always be recorded together with the results, including parameters such as:

- operation type
- object size
- concurrency
- test duration
- number of objects

This is important because benchmark results are only meaningful when the workload characteristics are known.

When comparing results, use the same Warp workload and execution path whenever possible.

## Notes

The benchmark workloads used in these tests have been tuned to approximate the S3 access patterns and load typically generated by a container image registry such as Red Hat Quay.

The objective is therefore not to determine the maximum theoretical performance of the S3 backend, but to evaluate its behavior under a registry-oriented workload.

Benchmark results depend heavily on the network path, object size, concurrency, S3 implementation, and underlying storage.

When comparing results, use the same Warp workload and execution path whenever possible.

## Workflow

The benchmark environment is deployed in the `noobaa-benchmark` namespace.

The workflow consists of:

1. Create the benchmark namespace.
2. Provision an S3 bucket using an ObjectBucketClaim (OBC).
3. Create persistent storage for Warp benchmark results.
4. Deploy the Warp client and its internal service.
5. Deploy the Warp analyzer.
6. Run the desired benchmark Jobs.
7. Analyze the generated benchmark data.

### 1. Create the Namespace

```bash
oc apply -f namespace.yaml
```

Verify:

```bash
oc get namespace noobaa-benchmark
```

### 2. Provision the S3 Bucket

Create the ObjectBucketClaim:

```bash
oc apply -f obc.yaml
```

Verify that the OBC is bound:

```bash
oc get obc -n noobaa-benchmark
```

The OBC automatically creates a `Secret` containing the S3 credentials and a `ConfigMap` containing the bucket connection information.

```bash
oc get configmap,secret -n noobaa-benchmark
```

### 3. Create the Results Storage

Benchmark data generated by Warp is stored on a persistent volume so that results remain available after individual benchmark Jobs are removed.

```bash
oc apply -f warp-results-pvc.yaml
```

Verify:

```bash
oc get pvc warp-results -n noobaa-benchmark
```

> [!NOTE]
> The manifest does not specify a `storageClassName`, allowing the cluster default StorageClass to be used.

### 4. Deploy the Warp Client

Deploy the Warp client and its Service:

```bash
oc apply -f warp-client.yaml
oc apply -f warp-client-service.yaml
```

Verify:

```bash
oc get pod,svc -n noobaa-benchmark -l app=warp-client
```

The Warp client listens on TCP port `7761` and is accessed by the benchmark Jobs through the `warp-client` Service.

The client status can also be verified from its logs:

```bash
oc logs warp-client -n noobaa-benchmark
```

Expected output:

```text
warp: Listening on 0.0.0.0:7761 Press Ctrl+C to exit.
```

### 5. Deploy the Warp Analyzer

Deploy the analyzer:

```bash
oc apply -f warp-analyzer.yaml
```

Verify:

```bash
oc get pod warp-analyzer -n noobaa-benchmark
```

The analyzer mounts the same `warp-results` PVC used by the benchmark Jobs and provides a persistent environment for inspecting and analyzing Warp benchmark data.

The installed Warp version can be checked with:

```bash
oc exec -n noobaa-benchmark warp-analyzer -- /warp --version
```

### 6. Run a Benchmark

Benchmark definitions are available under `Jobs/`.

For example, run the PUT smoke test:

```bash
oc apply -f Jobs/01-smoke-put-1m-c4.yaml
```

Monitor the Job:

```bash
oc get job,pod -n noobaa-benchmark \
  -l test=01-smoke-put-1m-c4
```

Follow the benchmark output:

```bash
oc logs -f -n noobaa-benchmark \
  job/01-smoke-put-1m-c4
```

The benchmark Jobs store their raw Warp data on the `warp-results` PVC.

Result filenames include a UTC timestamp to make individual benchmark executions easier to identify and correlate with cluster metrics and events:

```text
<UTC-timestamp>-<job/pod-name>.json.zst
```

For example:

```text
20260811T111447Z-01-smoke-put-1m-c4-zg5p5.json.zst
```

### 7. Analyze the Results

List the available benchmark results:

```bash
oc exec -n noobaa-benchmark warp-analyzer -- \
  ls -lh /results
```

Analyze a specific result:

```bash
oc exec -n noobaa-benchmark warp-analyzer -- \
  /warp analyze \
  /results/20260811T111447Z-01-smoke-put-1m-c4-zg5p5.json.zst
```

Alternatively, open a shell in the analyzer when reviewing multiple results:

```bash
oc exec -it -n noobaa-benchmark warp-analyzer -- /bin/sh
```

Then:

```bash
cd /results
ls -lh

/warp analyze <result-file>.json.zst
```

## Benchmark Suite

The `Jobs/` directory contains benchmark profiles covering different aspects of S3 performance.

The suite is organized into the following groups:

| Series | Purpose |
|---|---|
| `00-04` | Smoke tests |
| `10-16` | PUT object-size sweep |
| `20-26` | GET object-size sweep |
| `31-*` | PUT concurrency sweep |
| `40-42` | Metadata operations |
| `50-53` | Multipart upload tests |
| `60-63` | Mixed workloads |
| `70-72` | Stress tests |
| `80-82` | Soak/endurance tests |

The mixed workload profiles are designed to approximate the I/O characteristics of a container registry such as Quay. They are synthetic workloads and are not intended to reproduce Quay's exact S3 request distribution.

The stress tests are intended to identify saturation behavior rather than represent normal registry traffic, while the soak tests are intended to evaluate performance stability over longer periods.
